What this actually is

Not an app, not a library — a template repository holding the process itself: guardrails, agent prompts, quality gates, an audit ledger, and the CI wiring that connects them. You copy it once, answer a short interview, delete the bundled example, and wire in your own product.

🛡️ Seven binding guardrails

Production is read-only. All changes flow through pull requests. Agents never merge their own work, never fail silently, and always explain themselves in plain language. The rules live in one file (AGENTS.md) so they cannot drift.

🔌 Provider-neutral by construction

Workflows and prompts address models by role — judge, execute, challenge — never by vendor. One adapter file per provider owns the vendor-specific command shape, and a test suite fails the build if a vendor name leaks anywhere else.

⚔️ Adversarial second review

Every agent PR gets a judge review; add one optional API key and a second reviewer from a different model family challenges it — because a second draw from the same distribution shares the same blind spots. Missing key? It degrades to one opinion and says so. It never fails your PR.

📊 Floors that only ratchet up

Coverage, mutation and bundle-size floors ship uncalibrated — measured against your code by tools/measure-floors.sh, never someone else's finish line. Guard tests make lowering a floor a visible, reviewable act.

📜 Ledger: memory without steering

Every agent run appends one JSON line to an orphan branch. History is never instruction — agents take orders only from one operator-controlled file on the protected branch, so "old agent chatter" can never steer a future run.

💤 Nothing surprises you on day one

All five scheduled agents ship disabled. You dry-run each one (tools/run-agent.sh <agent> --dry-run), then enable them one at a time. No cron firehose, no surprise bill.

Quickstart — under 30 minutes

Everything below is local text substitution and repo settings. The interview makes no network calls and finishes in seconds.

  1. Create your repo from the template

    Click Use this template on GitHub, or clone and re-point the remote.

  2. Run the adoption interview

    It asks your product name, provider, model ids per role and alert channel, then rewrites every placeholder and prints exactly what is left to do by hand.

    tools/init.sh

  3. Add credentials

    At minimum AGENT_CLI_TOKEN — normally your agent CLI's subscription token, not an API key, so runs cost nothing beyond your existing flat monthly plan. The repo tells you the exact mint command:

    tools/run-agent.sh --check-credentials <agent>

  4. Watch the loop run once

    Open issue #1 against the bundled example, mention your agent, and watch the steward triage it, open a PR, and the reviews and gauntlet fire.

  5. Make your first human merge

    That's the whole loop — before any of your own code even exists. Then delete examples/, wire in your product, and calibrate the floors against it.

The 22-gate gauntlet

Gates are tiered so a PR is green in about two minutes, while the heavy artillery runs nightly. Swapping the reference stack for your own means swapping config files — the gate identities stay put.

FAST — blocks every PR

Unit tests, lint, coverage ratchets, architecture freeze, secret scan, workflow lint, repo hygiene, spec-artifact presence, harness guards. Green in ~2 minutes.

FULL — heavier, still per-PR

Integration tests against a real database container, migration validation, E2E + accessibility, diff-scoped mutation testing.

NIGHTLY — the long watch

Full mutation runs, dependency CVE audits, upstream API contract checks, flaky-test detection, and an operational watchdog — failures open GitHub issues, optionally pinging your alert channel.

Design principles you can hold it to

  • A human merges, always. CI green is necessary but never sufficient. The merge click is the one step that is never automated.
  • Degrade loudly, never silently. A missing optional credential downgrades a check and says so in the run summary. A dead agent and a healthy agent must never look the same.
  • History is not instruction. Ledgers record what happened; steering happens only through one operator-owned file, protected by branch protection rather than convention.
  • Nothing is calibrated to someone else's code. Every quality floor ships as an unset sentinel until you measure your own baseline — then it only moves up.
  • Lessons accumulate as tests. Every operational lesson is pinned by a harness-guard test, so it cannot be quietly lost by the next refactor.

Cost, honestly

The normal case is your existing agent-CLI subscription's flat monthly price — the steward, the judge reviews and every routine run on it, so the marginal cost of one more run is zero. The only place per-token spend can enter is the optional challenge reviewer (a second model family needs its own API key). Skip it and you lose a second opinion — never the system.
