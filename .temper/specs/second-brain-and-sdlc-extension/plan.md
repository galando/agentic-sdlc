## Approach

Implement all three parts of `docs/plans/second-brain-and-sdlc-extension.md` in one
pull request, matching the plan's own mechanical prescriptions (A6, B's four-file
shape, C1/C2/C3) as closely as the live tree's actual conventions allow — read the real
`.agents/config.yml`, `agents-scheduled.yml`, `pins.json`/`gen-pin-tests.sh`,
`agent-routines.md` and `agent-modes.md` first, then match their exact schema and
prose voice rather than inventing a parallel convention.

**Alternative considered and rejected:** landing Part A, then one agent per phase, then
Part C, as four-plus separate pull requests — the plan's own recommended sequencing.
Rejected because the operator explicitly asked for the whole plan in one pass after
being shown the sequencing tradeoff (see the session's `AskUserQuestion` exchange:
"Everything (Parts A, B, and C)" was chosen over the phased option). The cost of this
choice — a larger single diff, and the five new agents landing without individual
phase observation — is accepted deliberately, not overlooked.

## Blast Radius

- **The watcher ring.** Appending agents to `ledger.agents` moves the wrap point that
  `cfg_predecessor` derives — every doc and prompt naming the old predecessor
  (`challenger`) had to be found and corrected, not just the code. Grepped for the
  literal string across prompts, runbooks and tests; two prose sites and two tests
  needed the update, all found and fixed (see `tasks.md` Task 8).
- **The FAST-tier "exact context set" claims.** `docs/QUALITY-GATES.md`,
  `branch-protection.md`, `pr-validation.yml`'s header comment, `tools/adopt.sh`'s
  literal payload, and `docs/maintainers/demo-recreation.md` all separately assert
  "the N fast-tier contexts" as a specific enumerated set (7, now 8). Missing any one
  of them leaves a stale count or, worse in `tools/adopt.sh`'s case, a branch-protection
  payload that never requires the new gate. All five were found by grepping for the
  phrase and the individual context-string enumeration, not assumed from one file.
- **Generated files.** `ADOPTING.md` and `pins.generated.bats` are pure functions of
  the tracked tree; both were regenerated only after `git add`-ing the new files (the
  generators read `git ls-files`, so an untracked new file is invisible to them — this
  cost one regeneration cycle mid-build, see `tasks.md` Task 11).
- **No production code touched.** `examples/` is untouched; every change is to the
  harness itself (prompts, config, workflows, docs, one new lint tool). The bundled
  example product's own gates (backend/frontend) are unaffected.

## Decisions

- **New agents ship `enabled: false`**, matching every existing agent — Part B's own
  four-file contract, and `agents-scheduled.yml`'s "day one is a no-op" design.
- **Weekly cadence on distinct weekdays, `release` monthly** — chosen to avoid any
  cron collision with the five existing daily agents (which occupy 06:00-18:00 UTC) and
  with each other; all in the underused 09:00 UTC hour, on odd minutes per the existing
  "top of the hour is contended" convention.
- **`max-age-hours` overrides for all five new agents** — the default 12h liveness
  window assumes daily cadence; a weekly/monthly agent needs a window sized to its own
  schedule plus scheduler-drift margin, or its own absence check would falsely alarm
  every day it is not scheduled to run.
- **`health`'s liveness check now reads its predecessor's own `max-age-hours`
  override**, not the daily default — because the predecessor (`release`) is no longer
  daily. This is a small behavioural correction beyond what the plan explicitly asked
  for, made because the plan's four-file agent shape did not anticipate the
  cross-cutting effect of extending the shared ring with non-daily agents.
- **Retroactive spec directory.** This spec was written after the implementation, not
  before, because the work began as a direct, closely-scoped implementation of an
  already-detailed plan document (PR #18) rather than as fresh design exploration —
  the plan itself served the role `intent.md`/`plan.md` normally would. It is filled in
  now, before the pull request is opened, so gate 21 and a genuine reviewer both have
  the same artifact a forward-built change would carry.
